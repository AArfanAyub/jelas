## 6. Privacy

JELAS collects nothing. There is no account, no server, no analytics, no advertising,
and no crash reporting. All data is stored on the user's own device, encrypted with
AES-256-GCM under a key derived from the user's PIN. Nothing is ever uploaded.

## 7. Verifying these claims

You can check the two strongest claims yourself:

```bash
# 1. The app has no internet permission (expect only POST_NOTIFICATIONS,
#    RECEIVE_BOOT_COMPLETED and nothing else):
aapt2 dump permissions jelas.apk

# 2. No third-party code is bundled — the assets are plain, readable source:
unzip -l jelas.apk | grep assets/
```

Every shipped file is human-readable source in `assets/`. There is no minified vendor
bundle, no `.so` native library, and no binary blob of unknown origin.

## 8. How the encryption actually works (so you can describe it honestly)

1. You choose a 6-digit PIN. It is **never stored**.
2. A random 16-byte salt is generated, and (on Android) a random 32-byte secret is
   created and wrapped by a key that lives in the **Android Keystore** — hardware-backed
   where the device supports it.
3. The encryption key = `PBKDF2-SHA256(PIN, salt ‖ deviceSecret, 600,000 rounds)` → AES-256-GCM.
   The key is non-extractable and lives only in memory while the app is unlocked.
4. Your whole data store is written to IndexedDB as **one AES-256-GCM ciphertext**, with a
   fresh random IV each time. Receipt images are encrypted the same way.
5. A small "verifier" blob proves a PIN is correct without ever storing it.
6. Wrong PINs trigger an escalating lockout (5 s, then doubling, capped at 15 min), persisted
   across restarts.

**What this means in practice:** on Android, an attacker who copies your app's data files
off the phone still cannot crack the PIN offline, because they are missing the
hardware-bound secret. In a plain web browser there is no hardware secret, so protection
rests on the PIN alone — the app says so on its own Security page.

**Recovery caveat — please understand this before you publish:** because the key is bound
to the device, the `.jelas` backup is deliberately **not** device-bound. It is protected by
its own password (PBKDF2 + AES-256-GCM), so it can be restored on a new phone. That makes
the **backup password** the single most important secret for recovery — encourage users to
set a long one, and warn them that clearing app data without a backup is unrecoverable.

## 9. Publishing checklist

Before you put JELAS on GitHub, the Play Store, or hand it to friends:

- [ ] **Never publish the signing keystore or its password.** `jelas-android/jelas.keystore`
      and `jelas-android/keystore.pass` are gitignored — keep them that way. If the keystore
      leaks, anyone can build an update that Android will accept as yours.
- [ ] Keep a private copy of the keystore somewhere safe. Losing it means you can never
      ship an update to an already-installed copy.
- [ ] If you publish the source, the `assets/` folder inside the APK is the full app — anyone
      can read it. That is fine (it is original work), but do not put secrets in it.
- [ ] Review the trademark labels in section 4 and decide whether to keep or genericise them.
- [ ] Confirm the licence you want. `LICENSE` currently ships MIT.
- [ ] Note that JELAS is a record-keeping tool, not a financial service, and that it is not
      affiliated with any bank or wallet — the About screen already says this.
